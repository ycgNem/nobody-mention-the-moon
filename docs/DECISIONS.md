### D-001 · Title: "Nobody Mention the Moon" · 2026-10-30
Kept the working title. With proximity voice and trigger words, the title is now a rule in the game, not just a joke. Saying "moon" near the werewolf is the first thing every new group will do by accident.

### D-002 · Reworked from a single-player turn-based puzzle to a co-op party game · 2026-10-30
The original pitch was a single-player, turn-based social puzzle with progression ([ORIGINAL_PITCH.md](ORIGINAL_PITCH.md)).
Reworked to: **1–6 player online co-op, real time, first person, physics, proximity voice**. The table's "social board" stays as the core, now with several hands on it at once and voice as an input.
Kept: weaponized small talk, lies become rules, readable topic travel, quirks learned by watching.
Changed: turns → beats (~12–15 s), one "you" → a team of hosts, dialogue options → Small Talk wheel + voice + physical props.

### D-003 · No progression · 2026-10-30
No XP, unlocks, persistent currency, levels, campaign or meta-upgrades. Every dinner is self-contained, and all cosmetics are available from the start.
Replay value comes from: hidden guest types + rolled quirks + occasions + events + houses + relationships, and from players getting better.
Allowed: dinner seeds (shareable), per-dinner awards and results. Nothing is written to disk or to a server between dinners.

### D-004 · Stack: TypeScript strict + Vite + Three.js + Rapier + Colyseus · 2026-10-30
Follows the house rule (TypeScript for everything, Vite, Three.js for 3D). Rapier for WASM physics that runs on both client and server. Colyseus for authoritative rooms with room codes and reconnection. Versions to be pinned in M0.

### D-005 · Server-authoritative sim, pure rules in `shared/` · 2026-10-30
All rules are pure deterministic functions in `shared/sim`. They're tested, run on the server, and also power the M1 2D debug board. Clients predict only their own body and held props.

### D-006 · Speech stays on the device · 2026-10-30
Keyword spotting runs locally. Only matched vocabulary words (`{word, t}`) go to the server. Raw audio and full transcripts never leave the player's machine. Cloud speech APIs only as an explicit opt-in fallback, if at all.

### D-007 · Trigger words are optional · 2026-10-30
Nobody needs a mic to play. Typed chat hits the same triggers, and every voice-driven feature (invite, toast) has a non-voice path. Voice adds risk and comedy and isn't a requirement.

### D-008 · 3D assets are built by Blender Python scripts, rendered in Three.js · 2026-10-30
All models (house, props, characters, animations) are generated by `bpy` scripts in `blender/`, built headless with Blender 5.2.3 LTS (Steam install), and exported to `.glb` for Three.js. Gameplay data (colliders, seats, rooms, doors, interactables) is exported alongside as `.layout.json` from the same scene.
- **Why:** assets can be reproduced and diffed, changed by editing code, and the visual house and the rules' house come from one source.
- **Exception to "TypeScript for everything":** `bpy` only speaks Python, so `blender/` is the one Python folder in the repo. It's build-time tooling only. Nothing Python ships or runs in the game. All runtime code (client, server, shared) stays TypeScript.
- Built outputs are committed, so the game runs without Blender installed.

### D-010 · Dev ports: client 5240, server 2567 · 2026-10-31
Other local projects already listen on 5173–5200 (Last Lighthouse, Goblin Pension Plan…). Some of them listen on IPv6 `localhost` while Vite listens on IPv4, so a clash shows up as the *wrong game* loading, not as an error. The client uses `strictPort: 5240`. Override the server address with `VITE_SERVER_URL`.

### D-011 · Room codes are normalized by the client, and the server rejects anything else · 2026-10-31
Colyseus `filterBy(['code'])` matches the raw join option, so `moon` and `MOON` would become two separate dinners. Clients send `normalizeRoomCode(code)`. `DinnerRoom.onCreate` throws on any code that isn't 4 normalized characters, so a buggy client gets an error instead of a stray empty room. Found by the M0 integration test.

### D-012 · M1 is played in the 3D greybox, not on a 2D board · 2026-10-31
M0 already gives us a walkable room with six `seat_*` points, so M1's fun test runs there: guests are placeholder figures at the seats, an overhead camera (`O`) stands in for the board view, and actions come from aiming at things.
- The rules stay in `shared/sim`, independent of rendering and tested, so nothing is lost if the 3D side changes.
- The sim updates a plain `DinnerState` in place and returns a list of events. It stays deterministic (seeded RNG stored in the state, fixed step). That's cheaper than copying the state every tick, and it's still easy to replay and test.
- Solo for M1: the sim runs in the browser. Online players each get their own dinner until M3 moves it to the server.
- M2 shrinks to the physical layer (kitchen, carrying, full house, line of sight).
